# PROPOSAL — zkAge Proof: Privacy-Preserving Age Verification

**Author:** LexzCodes
**Date:** September 2026
**Track:** Zero-Knowledge dApp / Privacy & Identity
**Repo:** https://github.com/olatopeolajide1/LexzCodes

## 1. Executive Summary

`zkAge Proof` is a zero-knowledge dApp that lets any user prove **"I am at least 18 years old"** to a smart contract **without ever revealing their birth date**. The user's birth date and a personal secret never leave their browser: a Groth16 SNARK proof is generated client-side with snarkjs and submitted to an on-chain verifier on Sepolia. The contract stores only a boolean attestation per wallet plus an unlinkable nullifier that prevents proof replay or sharing.

Age checks are everywhere — exchanges, gaming, adult content, dating, DeFi KYC gating — yet today's solutions demand full identity documents or centralized attestation registries. This project demonstrates that a minimal, trustless, reusable alternative is practical today with commodity tooling (Circom + Groth16 + Hardhat + Next.js).

## 2. Problem Statement

Existing age verification models force an unacceptable trade-off:

- **Document KYC** (uploading an ID to a third party) exposes far more data than needed and creates honeypots of PII that get breached.
- **Centralized attestation services** (e.g., "XYZ-DAO says you're 18") introduce a trusted intermediary, are unusable cross-platform, and still link your identity to every service you use.
- **On-chain self-attestation** ("I confirm I'm 18") is trivially lieable and enforceable by no one.

The gap: a **self-sovereign, cryptographically enforceable** age gate. The user should hold their own credentials, reveal the *minimum* necessary fact (18+ yes/no — not the birthdate, not the exact age, not the document), and produce a proof any contract on any EVM chain can verify without trusting the prover or any oracle.

## 3. Proposed Solution

A Circom circuit compiles the statement:

> *"I know a valid calendar date (day, month, year) and a secret such that I have already had my 18th birthday as of the reference date, and nullifier = Poseidon(year, month, day, secret)."*

Key design decisions:

- **Client-side proving.** The wasm/zkey artifacts are served statically to the browser; snarkjs generates the proof locally. The birth date is typed into the page and never transmitted anywhere — not to a server, not on-chain, not in the proof.
- **Nullifier instead of identity.** `Poseidon(year, month, day, secret)` is published so the same birthdate+secret always maps to the same nullifier. A contract can therefore reject a copied/replayed proof while learning nothing about the birthdate. Different services cannot reverse it or correlate it to an ID document.
- **On-chain policy pinning.** The contract hard-requires the circuit's public `minAgeYears` signal to equal 18, so proofs generated under a different policy are rejected even if cryptographically valid.
- **Self-contained setup.** Powers-of-tau and phase-2 contributions are generated locally by script — no downloaded ceremony files, fully reproducible builds.

The dApp flow: connect wallet → enter birth date (in-browser only) → ZK proof generated in-browser → proof submitted to `AgeVerifier` on Sepolia → contract emits `AgeVerified`, the wallet is attested 18+, and any third-party contract can gate on `hasVerifiedAdult(address)`.

## 5. Privacy Model

What is revealed vs. protected:

| Data | Visible to anyone? |
|---|---|
| "This wallet is 18+" attestation | Yes (on-chain mapping) |
| Nullifier (Poseidon of birthdate+secret) | Yes — but one-way and unlinkable to an identity |
| Birth date (day/month/year) | **Never** — stays in browser memory |
| Secret | **Never** — stays in browser memory |
| Exact age / zodiac sign / ID documents | **Never** |

Trust assumptions:

- The reference date (`refDay/refMonth/refYear`) is chosen by the prover at proof time. The circuit guarantees 18+ *as of that date*, and the reference date is a public signal, so a relying party can require the anchor date to be recent (e.g., within N days of now) before accepting an attestation. The dApp always uses "today" (UTC).
- The setup is a local two-contribution + beacon ceremony, sufficient for a demonstration. A production deployment should use a public multi-party ceremony.
- Poseidon hides the birthdate computationally (preimage resistance); the nullifier is stable for the same (birthdate, secret) pair, which is what enables replay protection without identity leakage.

## 7. Roadmap / Future Work

1. **Issuance model** — replace self-claimed birthdate with proofs over signed ID credentials (e.g., anonymous credentials / ZK-KYC attestations) so the birthdate is *certified*, not self-declared.
2. **Verifiable reference time** — source the reference date from a block timestamp committed in-circuit, removing the prover's choice of anchor date.
3. **Age brackets & thresholds** — generalize to "21+", "65+" or committed age ranges without re-proving per threshold.
4. **Mobile UX** — witness generation currently takes a few seconds on desktop; optimize for mobile browsers and wallet-integrated dApps.
5. **Multi-chain** — the verifier is plain Solidity and deployable to any EVM network; add attestations cross-verified via a canonical deployment + bridges.

## 8. Conclusion

`zkAge Proof` shows the full arc of a production-shaped ZK application: a hand-written circuit with a real arithmetic statement, a complete Groth16 setup pipeline, a hardened on-chain verifier with replay protection, real tests that generate actual proofs, and a polished dApp that keeps all private data client-side. It is deployable, auditable, and extensible toward certified-credential age verification.
